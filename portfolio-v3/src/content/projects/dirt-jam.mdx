## Overview

Acerola's Dirt Jam is a community event encouraging participants to explore graphics and shader programming.
For this project, I started with the provided reference code and a list of suggested ideas to experiment with.

## Getting Familiar

<Split ratio="1:1">
    <div>
        Before jumping into new features, I first wanted to understand what I was working with.
        The jam provided an annotated terrain generator in Godot,
        so I went through the code and experimented with the available inspector parameters.
    </div>
    <div>
        I played around with the mesh settings, noise generation,
        octave count and material properties to get a better understanding of how they influenced the generated terrain.
        This gave me a starting point for deciding what I wanted to build on top of the existing implementation.
    </div>
</Split>

<Split ratio="1:1" reverse align="center">
    <div>
        The jam also provided a list of suggested features for participants looking for ideas.
        After considering which ones were most relevant to my plans,
        I settled on four to start with:

        - **Distance Fog** - introducing atmospheric depth.
        - **Shader Include Files** - reducing duplicated code between shader stages.
        - **Level of Detail** - adjusting terrain detail based on camera distance.
        - **Improved Lighting** - extending the existing Lambertian model with specular highlights.
    </div>

## Texture Mapping

Moving beyond the terrain's initial flat coloring,
I wanted to introduce actual surface textures.
This turned out to be the most challenging part of the project.
Getting triplanar texturing to work without unwanted stretching took several days of debugging.

I was struggling to get the textures and their associated resources to work correctly,
so I reached out to other jam participants.
`Refoulay` shared their implementation, which gave me a useful reference for troubleshooting my own.
After working through the initialization and texture-binding issues,
I eventually got the terrain rendering correctly.
I then extended the implementation to support different texture resolutions,
testing everything from 128px to 4K in the running scene.

<Split ratio="1:1">
    <div>

        ### Resources

        - [Beer's Law — volumetric rendering theory](https://cglearn.eu/pub/advanced-computer-graphics/volumetric-rendering)
        - [Fog theory walkthrough (video)](https://youtu.be/oQksg57qsRA?si=uunivFLk1rYETOH1&t=138)

    </div>
    <div>

        **Glossary** — a few terms if you're newer to graphics programming:

        - **CPU** — the computer's general-purpose "brain." Handles logic and game state, but is slower at graphics work.
        - **GPU** — specialized hardware for rendering and parallel calculations, essential for games and 3D visuals.
        - **Shader** — a small program that runs on the GPU to control how something looks: color, lighting, surface effects.
        - **Uniform** — a shared setting that stays constant across many pixels or objects, like a global color every shader can read.
        - **Buffer** — a block of GPU memory used to store data so shaders can access it quickly.
        - **Uniform Buffer Object (UBO)** — a shared "box of settings" (colors, lights, camera info) multiple shaders can read at once.
        - **Data Alignment** — how data is arranged in memory so it fits the slots hardware expects. Misaligned data wastes memory or slows things down.
        - **Texture Mapping** — applying a 2D image onto a 3D surface to add detail like grass, rock, or water.
        - **Low-level** — working with raw materials instead of prebuilt furniture. More control, more effort.

    </div>
</Split>

## Post Mortem

<Split ratio="1:1" align="center">
    <div>

        This project was my crash course into graphics programming, where I learned about concepts such as:

        - GPU Data Alignment
        - Generating Terrain Data
        - Rendering Terrain Data
        - Compositor Effects (Godot)
        - Graphics APIs (Vulkan, SPIR-V)

    </div>
    <div>

        My favorite takeaway was figuring out GPU memory alignment — and coming up with my own analogy to really understand it:

        > Think of UBO memory like an inventory grid. Each data type has its own slot size, and a row can only hold 4 slots.
        Bigger items (like `vec3` and `vec4`) get VIP spots at the start of the row, and smaller items fill in the gaps.
        If the order changes on the CPU side, you have to re-pack the layout to match on the GPU side.

    </div>
</Split>
