## Overview

<Split ratio="3:2" align="center">
    <div>

        Parachute Panic is my Unity take on Nintendo's 1981 Game & Watch *Parachute*, rebuilt from an earlier Processing version.
        I kept working on it because I still had to retake it, and because it overlapped well with the Git Gud module: the codebase needed improvement in nearly every aspect.

        In my version the emphasis lies less on catching parachutists and more on dodging obstacles.
        The player earns or loses points depending on their actions, which makes for a more active, risk-driven loop that serves the goal of the game: reaching the highest highscore.

        My own addition is a highscore system: the ten best scores, with player names, are stored locally and shown in the UI.

        This iteration focused on:

        - Improving code quality and structure
        - Processing peer feedback and playtests
        - Extending the old highscore system

## Design

<Split ratio="1:1">
    <div>

        ### Core design choices

        To make the gameplay more manageable I adjusted the spawn intervals and capped the maximum number of lives, balancing challenge and playability.

        The scoring system was reworked to encourage active play: players are rewarded for interacting and less for playing passively.
        This stops players from "beating" the game without taking any real risk.

        The original only had three positions (left, middle, right).
        For a modern version I wanted a movement range wide enough for the player sprite to fit across it about five times.

    <div>

        ### Art & sound

        The visual style is inspired by retro arcade games, with pixel art and simple colors for clear readability.
        I looked up Game & Watch sprite sheets and gave a few sprites a custom outline in Aseprite.
        The highscore screen draws on old-school arcade leaderboards.

        For audio I chose an arcade-inspired style, with sound effects that give clear feedback on positive and negative interactions.
        The music is deliberately calmer outside of gameplay, for contrast and to prevent overstimulation.

        ### Conventions

        I used a mix of Unity's conventions and the course guidelines.
        The ones I stuck to most:

        - English as the language of choice
        - PascalCase and camelCase, following the engine and language conventions
        - Opening curly bracket on the next line
        - Local variables at the top of a function, where possible
        - Group things that belong together without whitespace, and separate things that don't with a single blank line
        - Declaration order: public / protected / private, member variables before functions, engine hooks (`Start`, `Update`) before custom functions, functions in order of appearance
        - Always include access modifiers

    </div>

<Split ratio="3:2" reverse align="center">
    <div>

        **Delegates, Actions and UnityEvents.**
        I deliberately chose not to write custom UnityEvents, because they are less transparent: you have to go to the editor to see what something does.
        With Actions and delegates you can read directly which arguments are expected and passed along, and what the intent is, for example from an action named `OnDeath`.
        That made the code more readable and easier to debug.

        When the highscore list changes, an event fires and the UI reacts, so the UI has no direct dependency on the logic.

    </div>
    <div>

        ```csharp
        public delegate void OnHighscoreListChanged(List<HighscoreElement> list);
        public static event OnHighscoreListChanged onHighscoreListChanged;

        HighscoreHandler.onHighscoreListChanged += UpdateUI;
        ```

## Highscore System

<Split ratio="2:3" align="center">
    <div>

        The system was designed to store scores persistently, let players enter their initials, and stimulate competition and replay value.

        For storage I chose JSON over PlayerPrefs.
        JSON suits managing lists like leaderboards, it is more flexible and extensible, and it makes the stored data inspectable.
        PlayerPrefs is fine for quickly testing functionality, but it is tied to my machine (the registry shared by all my Unity projects) and not much use beyond that.

        I looked at roughly three approaches:

        - Keep scores while the game runs. Local only, so not really a highscore.
        - Write to a local JSON file. You'd want to encrypt it, otherwise players can cheat their highscore.
        - An online database. It has to be hosted, linked and set up.

    </div>
    <Media src="/images/caustics.svg" alt="UML class diagram of the highscore system" caption="UML: logic, data storage and UI are separated." />
</Split>

The system is built modularly:

- Scores are managed inside the system (`HighscoreHandler` decides whether a score makes the list, `ScoreHandler` tracks the current score)
- Data is saved and loaded through a separate file-handling layer (`FileHandler`, `JsonHelper`)
- The UI reacts to changes in the data through an event
- Entries are stored as a list of name and score, sorted by points

### The duplicate entry bug

<Split ratio="3:2" reverse align="center">
    <div>

        During implementation I ran into a problem in the flow of the system.
        The score was saved directly at game over, while the player hadn't been able to enter a name yet.
        That produced duplicate entries, because the name wasn't available at the moment of saving.

        The cause was the order of events: the game went straight from game over to saving the score, with no step in between for input.
        I adjusted the event flow with Unity Events so the order of actions is explicitly controlled: an intermediate `EnterName()` step after the `OnDeath` event, with the score only saved after input.

    </div>
    <div>

        ```csharp
        private void EnterName()
        {
            OnGameEnd?.Invoke();

            if (inputHandler.Name == "")
        {
            highscoreMenu.SetActive(true);
        }

            // A UnityEvent on the enter button of the EnterHighscoreWidget.
            // That's how it communicates to call -> StopGame() function.
        }
        ```

    </div>

### Do leaderboards actually motivate?

Highscores are often used to motivate players, but the effect depends heavily on how they are designed.

- **Leaderboard Design Principles to Enhance Learning and Motivation in a Gamified Educational Environment** found that leaderboards help players set goals and raise motivation, because players can compare their performance and get clear feedback. Not for everyone though: players low in the ranking can end up demotivated.
- **Dave's Overly Detailed Analysis of a Game System** describes scores as a sense of progression and reward that directly influences behavior: by giving certain actions more points, a developer can steer how players play.

The strength of highscores is that they combine motivation with feedback and encourage replaying.
The weakness is that they make competition central, which doesn't work for every player, and a badly balanced score system can cause frustration.
In Parachute Panic the score system rewards active play, with points for desired actions and penalties for mistakes, and highscores are visible in the menu so players can compare.
I expect that to raise motivation, but I know it won't have the same effect on everyone.

### Reflection

The system builds on several tutorials and some theory, but merging them and bridging them to my own context seriously tested me.
Debugging with breakpoints because the `highscoreList` wasn't supposed to be empty ("It worked in the tutorial!?").
Drawing a class diagram because I could no longer follow the communication between more than just this one system.

Extending it came down to pattern recognition: how can I reuse the fundamental base in my own use case.
It also took trial and error to grasp getters, setters and globals, and to understand that abstracting everything isn't always required.

## Feedback

Based on peer, playtest and teacher feedback I improved the project on both gameplay and code level.

<Split ratio="1:1">
    <div>

        ### Gameplay & balancing

        - **Too forgiving, not punishing enough** → bomb penalty raised to -10 → mistakes have direct impact, so weighing risk matters more
        - **Score could be farmed by ignoring objects** → parachutes +7, power-ups +3 → active play is rewarded, passive play discouraged
        - **Too much visual noise** → spawn intervals increased → better readability, less cognitive overload
        - **Unclear which objects to catch** → colors, sprites and a title screen explanation improved → faster onboarding
        - **Physics felt inaccurate** → tuned, but deliberately left slightly unstable → more challenge without full control

    </div>
    <div>

        ### UI & UX

        - **Unclear UI flow** → restart and menu functionality added
        - **Duplicate highscore entries** → intermediate `EnterName()` step → score is saved only after input
        - **Wish to see highscores outside Game Over** → highscore button reused in the main menu

        ### Code quality & refactoring

        - **Magic numbers** → replaced by variables → more readable, easier to tune
        - **Needlessly complex or unreadable code** → naming improved, unnecessary comments removed
        - **Unclear inspector variables** → renamed and documented → better usability for designers
        - **Direct dependencies between systems, like the ScoreManager** → deliberately kept, but I gained insight into event-driven alternatives
        - **`GameObject.Find()` is strongly discouraged** → usage minimized, direct references instead

    </div>
</Split>

Feedback played a central role in improving the project step by step.
Technical feedback in particular, like using events and reducing coupling, gave me a better understanding of scalable software architecture, which is valuable for future projects.

## Takeaway

    <div>

        I grew a lot in independence as a developer.
        Where I used to struggle with basics like loops and leaned heavily on external help, I can now write working, thoughtful code on my own.

        The key insight was the difference between code that "works" and code that is also readable, maintainable and future-proof.
        Refactoring and processing feedback made me think more consciously about structure, naming and responsibility.

        On the design side I learned that visual presentation and feedback play a big role in motivation, for the player and for me as a developer.

        If I started over, I would begin with a simple, well-structured base, like a minimal scene, and expand iteratively.
        I would also think about architecture and system structure earlier, to limit unnecessary refactors.
