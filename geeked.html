Intro

Way2Terrain began as an entry for the Dirt Jam. I debated using Unity or Godot, but went with Godot — it’s the recommended FOSS option, and the reference code was already written for it by Acerola, complete with helpful comments.

I had two concept ideas:
1) Way2Geeked — cloud rap vibes, experimental, geeked out.
2) Hueco Mundo but I’m already tackling that in another Unity project, so I shelved it.

Naturally, I went with Way2Geeked and built this moodboard to lock in the aesthetic. The spark came while I was listening to music and stumbled across the “Way2Geeked” visualizer on YouTube. All I could say 'bout it: “this shit trim, luh twin.”

Development

Way2Terrain came together through thugging it out and raw dogging any and every subject i had no pre-knowledge on. To brighten the odds, commercial engines like Unity and Unreal come with the luxury of already integrated pipelines that handle includes and automatic recompilation of shaders. Not to mention polished terrain systems.

Godot on the other hand does not. Which results in me having to understand what's happening under the hood. Take for example: Memory Layouts, Data Alignment and Pipeline Management.


Technical Challenges

  • • GPU Data Alignment – Data alignment, in computer science, is the practice of arranging data in memory on specific byte boundaries to optimize data access and processing

    messing up the order of data pushed to the Uniform Buffer or forgetting to add to padding to keep the struct 16-byte aligned will cause the gpu to read some data as Garbage GPU hardware wants data in chunks of 4 floats (vec4). So a vec3 → needs a dummy float to fill the last slot.

    • Shader Modularity – I built a GDScript-driven GLSL include loader, saving ~500 lines of duplicated shader code (loc).

    • Fog & Lighting – Implemented exponential fog using Beer's Law after failure using faulty math equations beforehand.

    – Implementing a new lightning model (Blinn-Phong) proved difficult due to my limited knowledge of such low-level rendering logic.

    • Texturing – After several failed OpenGL/Vulkan binding attempts, a tip from another jam participant cracked the code on sampler binding and UV mapping.
    This method implements Triplanar Mapping by adding Sampler Uniforms to Fragment shader only.

    – I also implemented the allowance of multiple texture sizes to be mixed and matched. Tested from 128p up to 4k textures.

Low-Level Rendering

While most engines have luxuries like built-in shader includes and automatic shader recompilation. Godot's lower-level approach forced me to understand what’s actually happening under the hood — and just how much these “automatic” features enhance the users' experience (UX).

One of the biggest challenges was learning about Uniforms, Uniform Buffer Objects (UBOs), and the rules of data alignment and padding. I reached out to other graphics programmers in the Dirt Jam community, and after a lot of back-and-forth, we landed on an analogy that finally clicked for me:


“Think of UBO memory like an inventory grid. Each data type has its own slot size, and the row can only hold 4 slots. Bigger items (like vec3 and vec4) get VIP spots at the start of the row, and smaller items fill in the gaps. If the order changes on the CPU side, you have to re-pack the layout to match on the GPU side.”

That “inventory puzzle” understanding was a turning point. From there, I could properly structure my UBOs, prevent GPU data corruption, and finally move on to implementing features like:


  • • Water Shader – Fragment-based displacement with Fresnel reflections integrated into Sky3D.

    • Post-Processing – Lens dirt, film grain, and Filmic tone mapping to push the mood.

Conclusion

Way2Terrain ended up being both a technical playground and a creative statement — proof that a game engine can be just as much about expression as simulation. However so the journey wasn’t without heartbreak... most notably, I missed the official submission deadline due to an incomplete itch.io page and a broken build. Still, I walked away with far more than screenshots:

  • Start builds and deployment testing early.
  • Respect the time sink of low-level systems; scope accordingly.
  • Sleep is a feature, not a bug.
